## Fase 8 — Lease offline (T064–T071)

- [x] T064 Implementar `GenerateOfflineLease` en `AssetHub.Application/Auth/` (claims `typ=offline_lease`, `tid`, `scope`, `device_id`, `jti`, TTL por tenant acotado a 4–24 h). **Desvíos**: (a) la emisión vive en `AssetHub.Infrastructure/Security/JwtTokenGenerator.cs` —el generador existente— y no en `AssetHub.Application/Auth/`: la interfaz (`IJwtTokenGenerator`) sí está en Application, pero el manejo de `JwtSecurityToken`/`SigningCredentials` es infraestructura y duplicar un segundo generador en Application partiría el material de firma en dos lugares; en Application quedan las reglas (`OfflineLeaseIssuer`: acotado de TTL, usuario activo, tenant, `deviceId`); (b) **la firma es RS256 con un anillo RSA propio, no "la misma clave que el access token"**: el access token firma HS256 sobre `JwtSettings:Secret` y publicar un JWKS de esa clave sería publicar el secreto con el que se firman todas las credenciales de API. El plan §6.1 y el spec §4.4 asumen un access token asimétrico; mientras no lo sea, el lease necesita su par RSA (`OfflineLeaseKeyRing`). Efecto colateral deseable: el lease no puede validar contra el API por construcción; (c) `iss` = `assethub` (minúsculas, como fija el spec) y `aud` = `field-pwa`, distinto del `aud` del access token para que un documento offline no se confunda con una credencial de API; (d) `jti` es UUIDv7 real (`AssetHub.Domain/Common/Uuid7.cs`), no `Guid.NewGuid()`: el spec lo pide ordenable y un v4 pierde esa propiedad; (e) el acotado `[4, 24]` **no** hace clamp: fuera de rango lanza `InvalidFieldAppSettingsException` → `422`, porque ajustar en silencio le mentiría al tenant sobre su autonomía real.
- [x] T065 Agregar `POST /api/v1/auth/offline-lease` en `AuthController.cs` (requiere access token válido; `deviceId` en el body). **Desvíos**: (a) el handler delega en `OfflineLeaseIssuer` (registrado en DI), compartido con T066, para que el acotado de TTL y la política no tengan dos implementaciones; (b) `deviceId` que no es UUID → `400 validation` con `errors.deviceId` (`device_id_invalid`), siguiendo el `format: uuid` del contrato, en vez de aceptar cualquier string; (c) usuario inexistente o inactivo → `403` (`UnauthorizedAccessException`, que en este repo mapea a 403 y no a 401 para no disparar el logout automático del SPA); (d) la respuesta incluye `jwks` y `requireDeviceLock` además de `leaseJwt`/`expiresIn`/`issuedAt`: el 021 §7 espera `jwks` en esta respuesta para cachear las claves **antes** de quedarse sin red, y `requireDeviceLock` es la única forma de que la política del tenant llegue al dispositivo. Es aditivo respecto del contrato 022, que se actualizó en el mismo cambio; (e) `issuedAt` y el `iat` del lease salen del mismo instante, para que el cliente calcule el vencimiento absoluto sin desfasaje.
- [x] T066 Emitir el lease también en `RefreshCommand` (respuesta opcional `offlineLease`). **Desvíos**: (a) el refresh pide el lease con un `deviceId` opcional; si no viene, no se emite y la respuesta queda idéntica a la anterior (`apps/web` no manda el campo, no cambia nada); (b) el lease va **anidado** (`offlineLease: { leaseJwt, expiresIn, ... }`) para que el cliente distinga "no pedí lease" de "pedí y vino `null`"; (c) la emisión ocurre **después** de persistir la rotación del refresh token: si la política del tenant está mal, el refresh token nuevo ya quedó guardado y el cliente no pierde la sesión; el error se propaga (no se traga) porque un `200` con `offlineLease: null` y un lease no emitido se ven igual en el dispositivo, y la diferencia se descubre recién al salir al campo.
- [x] T067 Implementar `GET /.well-known/jwks.json` (clave actual + anterior, `Cache-Control: public, max-age=86400`) fuera de `[Authorize]`. **Desvíos**: (a) se sirve con `MapGet` en `Program.cs` (no hay controlador ni convención de auth que lo alcance) y devuelve `kty`/`use`/`alg`/`kid`/`n`/`e` con base64url sin padding; (b) el anillo es singleton: importar el RSA por request no aporta nada; (c) si no hay claves configuradas se genera una **efímera** por proceso y se loguea un warning, en vez de fallar el arranque: los tests y el entorno local necesitan un JWKS válido, pero un reinicio invalida los leases (documentado en `docs/field-pwa/lease-rotation.md`); (d) el header del lease lleva `kid` y `alg=RS256` (lo pone `JwtHeader` desde `SigningCredentials`), que es lo que hace utilizable la rotación con solape; (e) una clave configurada que no se puede importar **sí** aborta el arranque: degradar a la clave anterior en silencio dejaría al servidor firmando con material que el operador cree retirado.
- [x] T068 Agregar `fieldApp.offlineLeaseHours` a la configuración de tenant + validación de rango. **Desvíos**: (a) se materializa como tabla `TenantFieldAppSettings` en la base del tenant (patrón `TenantInventorySettings`), con `Enabled`, `OfflineLeaseHours` (default 12) y `RequireDeviceLock`; migración `20261028183528_AddTenantFieldAppSettings`, índice único por `TenantId` y `ITimestamped`; (b) la fila es **opcional**: un tenant sin fila usa los defaults, así activar el módulo no exige backfill de configuración; (c) la validación vive en `OfflineLeaseIssuer` (única puerta de emisión) y se expone como `422 field_app_settings_invalid` con `offlineLeaseHours`, `minOfflineLeaseHours` y `maxOfflineLeaseHours` en el body, más un `detail` localizado (en/es); (d) **no se agrega endpoint de administración** en esta fase: la fila se provisiona/edita como configuración del tenant; `fieldApp.enabled` se persiste pero **no** se exige acá — el gate de login es T082.
- [x] T069 [P] Test `Field/OfflineLeaseTests.cs`: firma verificable con JWKS, `exp` correcto, lease de tenant A no valida para B, rechazo si el usuario está inactivo. **Desvíos**: 16 casos en 11 métodos —verificación real con `TokenValidationParameters` armados desde el `jwks` de la respuesta (`iss`, `aud`, `exp` sin skew), `kid`/`alg` del header, `jti` v7 (posición de versión), TTL por política (8 h) y default (12 h), rango fuera de política (`3`, `25`, `0`, `240`) sin clamp, usuario inactivo, `deviceId` inválido (`""`, `null`, no-UUID, `Guid.Empty`), lease de A contra el JWKS de B (`SecurityTokenException` + `tid` distinto), JWKS con actual+anterior y clave efímera de 2048 bits—.
