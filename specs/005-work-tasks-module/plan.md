# Implementation Plan: Work Tasks Module

**Branch**: `005-work-tasks-module` | **Date**: 2026-08-16 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/005-work-tasks-module/spec.md`

**Note**: This plan covers the full Work Tasks module (M14) for AssetHub, including list/Kanban views, task CRUD, assignment, state transitions, history, comments, notifications, and integrations with assets, incidents, maintenance orders, preventive plans, and task recurrences.

## Summary

Extend AssetHub with a complete Work Tasks module so maintenance teams can manage tasks generated by preventive plans, recurrences, incidents, assets, or created manually. The module provides a list view with filters, a Kanban board, task detail with history and comments, assignment and state change workflows, and in-app notifications. It also integrates tasks into the asset and incident detail pages.

## Technical Context

- **Language/Version**: .NET 10 (backend), TypeScript/React 19 (frontend)
- **Primary Dependencies**: ASP.NET Core, MediatR, Entity Framework Core, Cronos, React Query, Tailwind CSS, shadcn/ui
- **Storage**: SQL Server (tenant databases via Aspire)
- **Testing**: xUnit + WebApplicationFactory for backend integration tests; manual/smoke tests for frontend
- **Target Platform**: Web application (desktop browser, responsive where practical)
- **Project Type**: Full-stack web application with separated backend/frontend
- **Performance Goals**: Task list and Kanban load in under 2 seconds for up to 1,000 tasks per tenant
- **Constraints**: Multi-tenant; all queries must be tenant-scoped; state transitions must be validated server-side
- **Scale/Scope**: Expected thousands of tasks per tenant, hundreds of concurrent users

## Complexity Tracking

No constitution violations required. The following decisions are the main sources of complexity:

| Decision | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Kanban view | User asked for visual state management | List-only view would not provide the requested board |
| Task state transition validation | Requirements demand server-side validation | Free-form state changes would allow invalid transitions |
| Comments and history | Spec requires collaboration and audit trail | Without these, users cannot trace task lifecycle |
| Multi-source integrations | Tasks can originate from assets, incidents, plans, orders, recurrences | Isolated tasks would not match the requested integration |
| Notifications | Spec requires assignment and due-date alerts | Silent tasks would reduce accountability |

## Research Decisions

See [research.md](./research.md) for detailed rationale.

Key decisions:

1. **State transitions**: Use a simple server-side state machine: `todo → in_progress → done`, `todo → cancelled`, `in_progress → cancelled`. Additional transitions can be added later.
2. **Catalogs are manual**: Priority and Task Type catalogs are created manually by the user via the Catalogs module (M5). The task form filters catalogs by `TargetModulesJson` containing `"tasks"`. No auto-creation seed.
3. **Task creation context**: The task form accepts optional `assetId`, `incidentId`, `maintenanceOrderId`, `preventivePlanId`, or `taskRecurrenceId`. When provided, the form pre-selects the related entity and disables conflicting fields.
4. **Notifications**: Reuse the existing `Notification` entity and event-driven notification handlers for assignment and due-date reminders.
5. **History**: Every state change creates a `TaskStatusHistory` record with timestamp, user, from-state, and to-state.

## Phase Dependencies

- **Staff module queries (M13)** must be implemented FIRST: `GET /employees` and `GET /teams` are required for task assignment dropdowns. Domain entities exist; API queries and frontend are pending.
- **Backend foundation** (DbSets, DTOs, queries) must be complete before frontend list/detail.
- **Backend CRUD endpoints** must be complete before frontend form integration.
- **Catalog association**: The `tasks` module must appear in the catalog module selector so users can associate Priority/TaskType catalogs to it.
- **Asset/Incident task widgets** can be built in parallel with the main Tasks page once the `GetWorkTasks` endpoint exists.
- **Kanban view** can be built after the list view works.
- **Comments and notifications** can be built after core task CRUD is complete.
- **State synchronization** (task → incident/order) can be added after core task state transitions work.
