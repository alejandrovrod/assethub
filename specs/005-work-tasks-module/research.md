# Research: Work Tasks Module

**Feature**: Work Tasks Module (M14)
**Date**: 2026-08-16

## Decisions

### 1. State Transition Model

**Decision**: Use a simple server-side validated state machine with states `todo`, `in_progress`, `done`, `cancelled`.

**Allowed transitions**:
- `todo → in_progress`
- `todo → cancelled`
- `in_progress → done`
- `in_progress → cancelled`
- `done` and `cancelled` are terminal (no further transitions)

**Rationale**: The spec requires validation of state transitions. This minimal set covers the primary maintenance workflow without over-engineering. Additional states or transitions can be added later without breaking existing records.

**Alternatives considered**:
- Configurable transitions per tenant: rejected as over-engineering for the first release.
- Only `todo → done`: rejected because it does not reflect real in-progress work.

### 2. Catalog Defaults for Task Type and Priority

**Decision**: Reuse the `PreventivePlanCatalogDefaults` helper pattern to auto-create `tasktype` and `priority` catalogs with `preventive` and `normal` items if missing.

**Rationale**: The existing demo tenant lacks these catalogs, which caused FK errors when tasks were generated by preventive plans. Auto-creating defaults ensures tasks can always be created, while tenants can later customize catalogs through the Catalogs page.

**Alternatives considered**:
- Make `TaskTypeCatalogItemId` and `PriorityCatalogItemId` nullable: rejected because it requires a database migration and weakens data integrity.
- Throw a clear error when catalogs are missing: rejected because it breaks the out-of-the-box demo experience.

### 3. Task Creation Context

**Decision**: The task form accepts optional related entity IDs (`assetId`, `incidentId`, `maintenanceOrderId`, `preventivePlanId`, `taskRecurrenceId`). When one is provided, the form pre-selects it and marks the task as dependent (`IsIndependent = false`).

**Rationale**: Users want to create tasks from assets, incidents, and other contexts. A single reusable form with optional pre-selection keeps the UI simple and consistent.

**Alternatives considered**:
- Separate forms for each context: rejected because it duplicates code and fragments the UX.
- Force every task to have a related entity: rejected because independent tasks are valid (e.g., general maintenance reminders).

### 4. Notifications

**Decision**: Use the existing `Notification` entity and a MediatR event handler for assignment and due-date reminders.

**Rationale**: The codebase already has a `Notification` entity and an event handler pattern used by preventive plans. Reusing it minimizes new infrastructure.

**Alternatives considered**:
- Add a scheduled background service for reminders: rejected because the spec says the scheduler is external (cron). A cron endpoint can evaluate due tasks periodically.
- Real-time SignalR notifications: rejected as out of scope for the first release.

### 5. Task History and Comments

**Decision**: Record every state change in `TaskStatusHistory`. Store comments in `TaskComment`. Load both in the task detail view.

**Rationale**: The spec explicitly requires a timeline of state changes and comments. Both entities already exist in the domain.

**Alternatives considered**:
- Store comments as a single JSON blob on `WorkTask`: rejected because it complicates querying and collaboration features.
- Combine history and comments into a single unified activity feed entity: rejected because it adds unnecessary abstraction; the frontend can merge the two lists.

### 6. Kanban View

**Decision**: Implement a simple Kanban board with columns for each state. Dragging a card to another column calls the existing state-change endpoint.

**Rationale**: The user requested Kanban. A simple implementation using the existing state machine avoids complex drag-and-drop libraries beyond basic HTML5 drag and drop or a lightweight DnD library.

**Alternatives considered**:
- Full-featured Kanban with swimlanes and WIP limits: rejected as out of scope for the first release.
- No Kanban: rejected because it was explicitly requested.

## Open Questions (resolved)

- **Q**: Should tasks be editable after completion?  
  **A**: Yes, title/description/due date/assignee can be edited, but state changes must follow the transition rules. Terminal states cannot be changed to another state.
- **Q**: What happens when a task is created manually without any related entity?  
  **A**: It is saved as an independent task (`IsIndependent = true`) and appears in the general task list.
