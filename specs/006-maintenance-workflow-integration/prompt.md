# Implementation Prompt: Maintenance Workflow Integration

## Objective

Implement the feature defined in `spec.md` by unifying the state-machine flows and relationships among `Asset`, `Incident`, `MaintenanceOrder`, `WorkTask`, and `PreventivePlan`. The backend domain, application, EF configuration, migration, and tests described in this spec are already implemented. This prompt focuses on completing the remaining work, especially the frontend widgets and any backend polish needed to support them.

## Context

- Stack: .NET 10 backend (MediatR + EF Core), React/TypeScript frontend (React Query, Tailwind CSS, shadcn/ui components).
- Backend is in `asset-hub/src/backend/`.
- Frontend is in `asset-hub/src/frontend/apps/web/src/`.
- Existing specs: `spec.md`, `plan.md`, `data-model.md`, `contracts/api.md`, `contracts/ui.md`, `tasks.md`, `quickstart.md`, `diagrams/workflow-state-machine.md`.
- Backend tests are in `asset-hub/tests/backend/AssetHub.Api.Tests/`.

## What is Already Done

- Inverse navigation properties added to `Asset`, `Incident`, `MaintenanceOrder`, `PreventivePlan`.
- State constants created: `IncidentStates`, `MaintenanceOrderStates`, `MaintenanceOrderKinds`, `WorkTaskStates`.
- `MaintenanceOrderStateTransitionValidator` and missing transition commands (`Start`, `Complete`, `Cancel`).
- Event-driven coordination:
  - `IncidentAssignedEvent` → creates corrective order.
  - `MaintenanceOrderStartedEvent` → starts child tasks.
  - `WorkTaskStateChangedEvent` → completes parent order when all tasks are terminal.
  - `MaintenanceOrderVerifiedEvent` → closes linked incident.
- Guards: `IncidentClosingGuard`, `PreventivePlanExecutionGuard`.
- EF configuration updated; migration `20260818202613_LinkMaintenanceWorkflows` generated.
- API endpoints: `PATCH /api/v1/maintenance-orders/{id}/start|complete|cancel`.
- 47 backend integration tests passing.

## What Must Be Implemented

### 1. Frontend Detail Widgets

Implement or extend the following UI components so users can see and act on the integrated workflow. Reuse existing services, hooks, and shadcn/ui components wherever possible.

#### Asset Detail Page (`pages/assets/detail.tsx`)

Add four read-only widgets (or sections):

- **Active Incidents**: list incidents with state `reported`, `triaged`, `assigned`, or `in_progress`; link to `/maintenance/incidents/:id`.
- **Maintenance Orders**: list orders for the asset; show kind, state, title; link to `/maintenance/orders` with query param `?orderId=:id`.
- **Work Tasks**: list tasks for the asset; show state, assignee, due date; link to `/maintenance/tasks` with query param `?taskId=:id`.
- **Preventive Plans**: list plans targeting this asset or its template; show name, next run, active flag; link to `/maintenance/preventive-plans`.

#### Incident Detail Page (`pages/maintenance/incident-detail.tsx`)

- Show the corrective `MaintenanceOrder` generated from this incident (if any): title, state, scheduled dates, assigned employee; link to order detail.
- Show child `WorkTasks`: title, state, assignee, due date; link to task detail.
- Disable the "Close Incident" action if the incident has active orders or non-terminal tasks. Show a tooltip explaining why.

#### Maintenance Order Detail Page (`pages/maintenance/orders/components/maintenance-order-detail.tsx`)

- Add action buttons: `Start`, `Complete`, `Verify`, `Cancel` (in addition to existing `Approve`, `Schedule`).
- Enable only buttons that correspond to valid transitions from the current state.
- Show child tasks with progress: `(done + cancelled) / total`.
- When all tasks are terminal, show a "Ready to complete" badge.
- Show related links: asset, incident (if corrective), preventive plan (if preventive).

#### Preventive Plan Detail Page (`pages/maintenance/preventive-plans/index.tsx`)

- Add a "Generated Items" section with two tabs: `Tasks` and `Orders`.
- List items generated by the plan with state and target asset.
- Make each item a clickable link to its detail.

#### Work Task Detail Page (`pages/maintenance/components/work-task-detail.tsx`)

- Show the most specific parent as a clickable link, following this priority:
  1. Maintenance order → `/maintenance/orders?orderId=:id`
  2. Incident → `/maintenance/incidents/:id`
  3. Preventive plan → `/maintenance/preventive-plans?planId=:id`
  4. Asset → `/assets/:id`
- If `IsIndependent == true`, show "Independent task".

### 2. Kanban Integration

In `pages/maintenance/tasks.tsx` and `pages/maintenance/components/work-task-kanban.tsx`:

- When a task card is dragged to `done`, after the state change succeeds, refresh the parent maintenance order detail if it is open.
- Optionally show a toast when the parent order auto-completes as a result.

### 3. Backend Polish for Frontend

If any of the following is missing, add it:

- Queries that include related entity names in responses so widgets do not need multiple round trips.
- Endpoint or query to fetch tasks/orders/incidents/plans by parent ID if it does not exist.
- Ensure `GetMaintenanceOrderByIdQuery` includes child tasks with state and assignee names.
- Ensure `GetIncidentByIdQuery` includes the generated corrective order and child tasks.
- Ensure `GetAssetByIdQuery` includes related counts or lightweight lists needed by widgets.

### 4. Tests

- Add or update frontend component tests if a test framework is already in use.
- Add backend integration tests for any new query you add.
- Ensure `dotnet test tests/backend/AssetHub.Api.Tests/AssetHub.Api.Tests.csproj` still passes (currently 47 tests).

## Implementation Rules

1. **Minimal changes**: do not refactor unrelated modules. Extend existing components rather than rewriting them.
2. **Match existing conventions**: use the same patterns for services, hooks, validation, and error handling already present in the codebase.
3. **Constants**: use the backend state constants when comparing states in TypeScript. Define a matching frontend enum or const object in a shared location if one does not exist.
4. **No duplicate work**: before adding a new query, check if an existing one can be extended with an `Include` or projection.
5. **Keep tests green**: run the backend test suite after any backend change.

## Verification Steps

1. Build backend: `dotnet build src/backend/AssetHub.Api/AssetHub.Api.csproj`
2. Run backend tests: `dotnet test tests/backend/AssetHub.Api.Tests/AssetHub.Api.Tests.csproj`
3. Start frontend dev server and manually validate each widget listed above.
4. Follow the scenarios in `quickstart.md` from the UI perspective.
